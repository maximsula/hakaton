# Mesh-доставка Wildberries

Общий бэкенд заказов, остатков, маршрутизации и начислений. Python 3.11+, FastAPI, Pydantic, SQLAlchemy и SQLite.

## Запуск

Из корня репозитория в PowerShell

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r backend/requirements-dev.txt
.\.venv\Scripts\python.exe -m uvicorn backend.app.main:app
```

Swagger UI доступен по адресу [http://127.0.0.1:8000/docs](http://127.0.0.1:8000/docs), схема по `/openapi.json`. Фронтенд может отправлять запросы на относительные адреса `/api/…` через прокси Vite.

При первом запуске приложение создаёт `mesh.sqlite3`. Если уже есть база первой версии, приложение добавит таблицы окон, рейсов и начислений и один раз рассчитает выплаты для ранее подтверждённых операций по текущим пилотным ставкам. Сохранённые начисления сохраняют исходную ставку. Для отдельной базы укажи новый путь через `MESH_DB_PATH`. Параметры читаются при запуске из `config/pilot.json`. Для отдельной конфигурации задай `MESH_PILOT_CONFIG`.

Проверки

```powershell
.\.venv\Scripts\python.exe -m pytest backend/tests -q
```

## API для фронтенда

| Метод и путь | Назначение |
|---|---|
| `PUT /api/points/{point_id}` | Зарегистрировать ПВЗ. Тело содержит `name` и `capacity_cm3`. |
| `GET /api/points` | Список ПВЗ, физическая занятость, доступный объём с учётом резерва. |
| `PUT /api/products/{sku}` | Зарегистрировать SKU для сценария без местного запаса. Тело содержит `seller_id` и `unit_volume_cm3`. |
| `GET /api/products` | Каталог. SKU также появляется после успешной приёмки. |
| `POST /api/batches` | Приёмка партии продавца. |
| `GET /api/inventory?point_id=A&sku=CABLE` | Остатки по партиям и состояниям. Фильтр `seller_id` доступен для кабинета продавца. |
| `POST /api/orders` | Создать заказ, рассчитать маршрут и зарезервировать остаток. |
| `GET /api/orders?point_id=A&actionable=true` | Очередь действий для ПВЗ. Доступен фильтр `status`. |
| `GET /api/orders/{order_id}` | Карточка со статусом, маршрутом, сроком, причиной выбора, `next_actions`, партиями заказа и историей. |
| `POST /api/orders/{order_id}/actions` | Подтвердить операцию над заказом. |
| `POST /api/inventory/{point_id}/{batch_id}/actions` | Сверка недостачи, перенос или вывоз долго хранящегося товара, отправка брака. |
| `POST /api/inventory/{point_id}/{batch_id}/storage` | Подтвердить хранение партии за текущие сутки UTC. Тело содержит `request_id` и `quantity` в товаро-днях. |
| `GET /api/operations` | Подтверждённые операции. Фильтры `point_id`, `order_id`, `batch_id`. |
| `GET /api/accruals?point_id=A` | Начисления и итог в копейках. Фильтры `point_id`, `order_id`, `batch_id` сочетаются. |

У всех POST есть `request_id`. Создавай новый UUID на действие и повторно используй его при сетевом сбое на том же запросе. Повтор успешного действия возвращает текущее состояние объекта. Изменённый запрос под тем же идентификатором получает `409 request_id_conflict`. Код партии уникален независимо от `request_id`.

Отказы бизнес-операций возвращают `detail.code` и `detail.message`. При отсутствии маршрута `detail.reason_code` содержит причину логистики. Ошибки структуры запроса возвращают стандартный список FastAPI с кодом `422`. Для кнопок бери тип и ПВЗ из `next_actions`. После ответа обновляй карточку и остатки. При оформлении учитываются ожидаемые поступления по другим заказам. Свободное место перепроверяется при фактической приёмке.

В `route` доступны `reason_code`, `trip_id`, `cost_breakdown`, `milestones` и `evaluations`. Последнее поле показывает рассмотренные маршруты и причины отклонений. `alternatives` включает варианты с рассчитанной ценой и сроком, даже когда срок превышает обещанный. `estimated_unit_cost_kopecks` — стоимость одного заказа целиком, в том числе если в заказе несколько единиц. У хаба `source_point_id` остаётся `null`, его идентификатор доступен в `hub_source_id`.

## Сквозной пример в Swagger

1. Создай ПВЗ `A` и `B` через `PUT /api/points/{point_id}`. Для обоих укажи `capacity_cm3: 1000` и соответствующее имя.
2. Прими три кабеля через `POST /api/batches`. Подставь дату поставки в прошлом с часовым поясом.

```json
{
  "request_id": "demo-receipt",
  "batch_id": "lot-1",
  "point_id": "A",
  "sku": "CABLE",
  "seller_id": "seller-1",
  "quantity": 3,
  "unit_volume_cm3": 100,
  "delivered_at": "2026-01-01T10:00:00+03:00"
}
```

3. Создай заказ через `POST /api/orders`. Подставь `promised_by` на два дня вперёд от момента запуска.

```json
{
  "request_id": "demo-order",
  "sku": "CABLE",
  "quantity": 1,
  "pickup_point_id": "B",
  "wb_club": true,
  "promised_by": "2026-12-01T18:00:00+03:00"
}
```

4. Скопируй `id` и `scan_code` из ответа. Отправь четыре запроса в `POST /api/orders/{order_id}/actions` с этим `scan_code` и разными `request_id`.

| `type` | `point_id` | Итоговый статус |
|---|---|---|
| `pack` | `A` | `packed` |
| `handoff` | `A` | `in_transit` |
| `receive` | `B` | `ready` |
| `issue` | `B` | `delivered` |

Итог в `GET /api/inventory` — `available: 2` в A и `in_transit: 0`. В карточке заказа видны четыре начисления на 45 ₽ по ставкам из архива Димы. Приёмка исходной партии оплачивается отдельно и видна в кабинете ПВЗ А. Повтор выдачи с тем же `request_id` возвращает прежний результат. У местной полки действие `pack` сразу переводит заказ в `ready`. Для хаба действие `confirm_hub_delivery` в точке выдачи создаёт моделируемую поставку и переводит заказ в `ready`.

## Исключения и пилотные правила

- `cancel` освобождает резерв до отправки. Собранный заказ с местной полки можно отменить до выдачи.
- `shortage` блокирует спорный остаток и пересчитывает маршрут без прежнего источника. Можно передать `shortage_quantity` и `shortage_batch_id`. Без количества блокируется весь резерв заказа. При отсутствии маршрута сохраняется `awaiting_route` с причиной. `reconcile_found` и `reconcile_missing` фиксируют результат сверки указанной партии.
- `replan` позволяет пересчитать маршрут до отправки, исключая сорвавшийся рейс. Передай `reason`, чтобы сохранить причину в истории. Для груза в пути `update_transit` принимает `actual_position` и, опционально, `remaining_travel_minutes`. Если минуты опущены, используются прежний прогноз прибытия или пилотная длительность поездки для заказа из старой базы. При отсутствии окна приёмки `ready_at` возвращается как `null`. Повторное наблюдение может восстановить срок и окно.
- `return_good` и `return_damaged` фиксируют результат осмотра полного заказа после выдачи. Годный товар становится доступным в ПВЗ возврата. Брак остаётся в состоянии `damaged` до действия `send_damaged_to_hub`.
- `storage_days` отсчитывается от исходной даты поставки партии и сохраняет смысл после переноса. Пилотный порог длительного хранения — 30 полных дней, его можно изменить в конфиге. `move_slow` подтверждает завершённый перенос и требует `destination_point_id`. `remove_slow` фиксирует фактический вывоз. Оба действия используют `quantity`.

## Настройка маршрутов и ставок

Модули Димы из `rwb-logistics-v2` находятся в [`backend/app/routing`](backend/app/routing) и [`backend/app/pricing`](backend/app/pricing). Сервис заказов передаёт остатки, город и окна точек, загрузку рейса и срок. Заказ, остаток, ёмкость выбранного рейса и окна резервируются в одной транзакции. При конкурирующем изменении снимка маршрут пересчитывается перед подтверждением. При отмене и пересчёте освобождаются ещё не использованные места.

- По умолчанию расписание моделируется. Для ПВЗ используется синтетический город, открытые суточные окна UTC и периодические отправления. Обычная доставка через хаб использует моделируемый срок `hub_minutes` и свободный объём ПВЗ выдачи.
- Для явных окон заполни `demo_routing.points` объектами из схемы [`PickupPoint`](backend/app/routing/models.py). Ключ словаря равен `pvz_id`. Каждое окно задаёт `window_id`, `start`, `end` с часовым поясом и `free_units` после вычета ёмкости под обычную выдачу. Пустой список закрывает соответствующий тип операции. Для конкретных отправлений заполни `demo_routing.direct_trips` объектами `DirectTrip`. Пустой список отключает рейсы. `hub_minutes: null` отключает моделируемое предложение хаба.
- В контрольном расчёте Степана 10 заказов дают в среднем 162 ₽ за заказ прямым рейсом, 8 заказов — 185 ₽, хаб — 172 ₽. Для переключения загрузки измени `trip_orders` и перезапусти приложение. `retained_hub_unit_kopecks` добавляет сохраняющиеся расходы к прямому варианту. При равной стоимости доступных вариантов выбирается хаб.
- `logistics_pricing.operation_rates` содержит учебные выплаты из архива Димы. Это отдельные ставки за подтверждённые операции. Каждая выплата хранится в той же транзакции, что и операция, с её `event_id` в качестве ключа. Для хранения допускается одно подтверждение на партию, ПВЗ и день UTC. `pricing_pending` оставлено в ответах API для совместимости и равно `false`.
